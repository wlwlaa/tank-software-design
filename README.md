# tank-software-design

Учебная игра на Java и LibGDX. Движение: стрелки или WASD, стрельба: пробел,
показать/скрыть полоски жизней: L.

## Домашнее задание 7: жизни, «Команда» и «Декоратор»

Все танки начинают со 100 единиц здоровья. Используется существующая модель
урона; `Tank.getMaxHealth()` хранит начальное здоровье для расчёта заполнения
полоски, в том числе при настройке другого значения через `TankWorld`.

По умолчанию полоски скрыты. Нажатие L показывает их у всех танков игрока
и AI, повторное нажатие скрывает. Это работает как во время движения,
так и на остановке, одновременно с движением и стрельбой.

- **Команда:** `ToggleHealthBarsCommand` переключает общий получатель
  `HealthBarVisibility`. `KeyPressCommandInputAction` выполняет команду только
  при переходе клавиши из отпущенного состояния в нажатое: удерживание L
  не вызывает повторного переключения каждый кадр.
- **Декоратор:** `HealthBarRenderer` реализует `SceneRenderer`, оборачивает
  `TankRenderer` и после отрисовки танка добавляет полоску, если она включена.
  Полоска следует за танком с той же интерполяцией, уменьшается при уроне
  и меняет цвет от зелёного к красному. `TankRenderer` менять не требуется.

`DesktopGameFactory` собирает команды, обработчики ввода и декораторы.
Все декораторы используют общее состояние видимости, включая танки,
добавленные позже через события `WorldSceneRenderer`. При удалении танка
декоратор освобождает свою текстуру и вложенный рендерер.
Деревья и пули не имеют здоровья и отрисовываются прежними рендерерами.

Тесты без OpenGL проверяют переключение, удерживание и повторное нажатие,
отрисовку танка при скрытых полосках, движение и урон, нестандартное и нулевое
начальное здоровье, общую видимость, добавление танков и освобождение ресурсов.

## Домашнее задание 6: стрельба, урон и «Наблюдатель»

`ShootCommand` хранит получателя `ShootingTarget` и вызывает `shoot()` только
при выполнении команды, по аналогии с `MoveCommand`. Игрок стреляет по пробелу,
в том числе во время движения. Пробел имеет приоритет перед выбором нового
направления. AI перед новым действием случайно выбирает одну из пяти команд:
четыре направления или выстрел. Рекомендательный движок в этом задании
не используется.

`Tank.shoot()` создаёт пулю через переданное окружение `TankWorld`. Пуля
появляется в следующей клетке по направлению танка и сохраняет это направление
на весь полёт. При создании сразу проверяется столкновение: выстрел в упор
не пролетает сквозь соседний танк или дерево. Собственный танк исключён из
проверки, поскольку при движении он резервирует и клетку перед собой.

`Bullet` обновляется вместе с другими `LevelObject`. Столкновение с деревом,
танком или другой пулей удаляет её из уровня; встречные пули удаляются обе.
Дерево остаётся на месте, танк получает урон. Выход за границу тоже удаляет пулю.
Длинный кадр разбивается по моментам перехода пуль в следующую клетку, чтобы
проверить весь путь и не пропустить встречную пулю. Уничтоженные объекты
безопасно удаляются во время обновления и больше не обновляются.

По умолчанию у танка 100 единиц здоровья, урон пули — 25, время полёта через
клетку — 0,1 секунды, интервал выстрелов — 0,4 секунды. Удерживание пробела
повторяет выстрелы с этим интервалом. Параметры задаются через `BulletSettings`
и конструктор `TankWorld`. По условию танк удаляется при здоровье **строго
меньше нуля**: при нуле он ещё жив, поэтому требуется пять попаданий.
Уничтоженный танк освобождает исходную и целевую клетки и не выполняет
даже ранее выбранные команды.

`TankWorld` публикует события `WorldListener.objectAdded/objectRemoved`.
При подписке наблюдатель получает все существующие объекты через `objectAdded`.
Так начальная сцена и изменения во время игры используют один механизм.
`WorldSceneRenderer` подписывается на мир, создаёт рендерер для каждого
танка, дерева и пули, а при удалении объекта сразу освобождает его графику.
`DesktopGameFactory` задаёт фабрику рендереров без ручного обхода объектов
для построения сцены. При завершении игры наблюдатель отписывается.

Один кадр `GameSession` проходит четыре этапа:

1. `TankSimulation.handle()` собирает команды всех контроллеров.
2. Затем выполняет собранные команды.
3. `TankWorld.update(tick)` обновляет оставшиеся объекты и столкновения.
4. Представление рисует актуальную сцену.

Новые тесты проверяют стрельбу в четырёх направлениях и при движении,
выстрелы в упор, деревья и границы, встречные пули, длинный кадр, здоровье
и уничтожение танков, перезарядку, события наблюдателя, освобождение графики
и порядок всех четырёх этапов без OpenGL. Всего проходят 142 теста.
Запуск окна на текущем ARM JDK 13 останавливается до создания сцены при
загрузке `libgdx.dylib` из LibGDX 1.9.11; визуальная проверка недоступна.

## Домашнее задание 5: танки, «Команда» и «Стратегия»

При запуске создаётся танк игрока и до трёх AI-танков в случайных свободных
клетках. Если места меньше, создаётся столько танков, сколько помещается.
Это работает и для случайного уровня, и для уровня из файла; формат файла
и параметры запуска остаются прежними. Игрок появляется в клетке `X`
файлового уровня или на стартовой позиции случайного уровня.

AI выбирает одно из четырёх случайных направлений или стрельбу перед новым действием.
Если путь закрыт, следующая попытка происходит в следующем кадре.
Во время движения новое направление не выбирается. Только танк игрока
реагирует на клавиатуру.

| Класс | Ответственность |
| --- | --- |
| `Command`, `MoveCommand` | Команда хранит танк-получатель и направление; движение начинается при `execute()` |
| `MovementStrategy` | Стратегия выбирает следующую команду |
| `KeyboardMovementStrategy` | Выбирает команду по стрелкам/WASD с прежним приоритетом клавиш |
| `RandomMovementStrategy` | Выбирает направление или выстрел через переданный `Random` |
| `TankController` | Выбирает команду для активного танка; во время движения разрешает стрельбу игрока |
| `TankWorld` | Хранит и обновляет объекты, проверяет столкновения, публикует добавления и удаления |
| `RandomTankGenerator` | Размещает танки без повторов; завершает перебор даже на заполненном поле |
| `TankSimulation` | Собирает модель и контроллеры без графического контекста |
| `DesktopGameFactory` | Подключает клавиатуру LibGDX и отрисовку всех танков |

`Tank` реализует `Obstacle`: при переезде заняты одновременно исходная
и целевая клетки. Цель резервируется сразу при выполнении команды,
а исходная клетка освобождается после завершения шага. Это запрещает
встречный обмен клетками и движение двух танков в одну цель. Проверка
границ в `Field` применяется одинаково к игроку и AI.

Количество AI-танков и длительность шага задаются в `DesktopGameFactory`
константами `AI_TANK_COUNT` и `MOVEMENT_DURATION`. Генератор и случайная
стратегия принимают `Random`, чтобы воспроизводить сценарии в тестах.

Тесты без окна проверяют генерацию, команды и стратегии, клавиатуру,
движение всех танков, резервирование и освобождение клеток, столкновения,
границы и совместную работу через `GameSession`.

## Домашнее задание 3: OCP и DIP

Ветка `hometask-3` основана на последнем коммите `hometask-2` (`e30d280`).
По заданию Pull Request направляется из `hometask-3` в `hometask-2`.

| Было | Стало | Принцип |
| --- | --- | --- |
| `Field` хранил только `Tree` | `Field` принимает любые реализации `Obstacle` | OCP, DIP |
| `Tank` зависел от `Field`, время движения было константой | Проверка движения задаётся через `MovementPolicy`, время шага передаётся в конструктор | OCP, DIP |
| `MovementInputAction` обращался к `Gdx.input`, знал `Tank` и фиксированные клавиши | Зависит от `KeyState` и `MovementTarget`, получает список `DirectionKeyBinding` | OCP, DIP |
| `TankGame` создавал модели, обработчики и графику | `GameSession` работает с `InputAction`, `Updatable` и `GameView`; зависимости собирает `DesktopGameFactory` | DIP |
| `FieldRenderer` создавал и рисовал деревья, `TankRenderer` зависел от `FieldRenderer` | Список `SceneRenderer` расширяется новыми реализациями; позиционирование задаётся через `TilePositioner` | OCP, DIP |

`DesktopGameFactory` — точка сборки приложения. Здесь выбираются карта,
текстуры, начальные координаты, время шага (0,4 секунды), клавиши и
интерполяция. Изменение этих настроек не требует изменения игровой логики.
Фабрика вызывается в `TankGame.create()`, когда графический контекст уже готов.

Для нового препятствия реализуйте `Obstacle` и передайте его в `Field`.
Для другого управляемого объекта реализуйте `MovementTarget`; для другого
источника ввода реализуйте `KeyState`. Для нового объекта сцены реализуйте
`SceneRenderer` и включите его в список представления. Конкретные реализации
подключаются в точке сборки; ядро при этом не меняется.

Модель использует `GridPoint2` из LibGDX, но не зависит от
глобального ввода, рендереров или графического контекста. Запрет нового шага
во время движения обеспечивается самим `Tank`, а не только клавиатурой.
Представление освобождает текстуры, рендерер карты, карту и `Batch`.

## Запуск и проверка

Проект использует Gradle 6.1.1. Для этого wrapper используйте JDK 13
(системный JDK 21 с этой версией Gradle несовместим).

```sh
./gradlew test
./gradlew run
```

При нескольких установленных JDK на macOS:

```sh
JAVA_HOME=$(/usr/libexec/java_home -v 13) ./gradlew test
JAVA_HOME=$(/usr/libexec/java_home -v 13) ./gradlew run
```

Тесты проверяют границы и препятствия, движение и длительность шага,
настраиваемые клавиши и их приоритет, защиту от повторного шага,
последовательность ввода/обновления/отрисовки и позиционирование спрайтов.
Интеграционная проверка `GameSession` запускает ввод и модель с заменой
представления без окна и OpenGL.

Итоговая проверка задания 5: 117 тестов прошли, ошибок и падений нет;
из них 47 добавлены для новой логики и интеграции. После каждой фичи
запускались соответствующие тесты, затем полный набор через JDK 13.
Запуск окна на текущем Mac с ARM JDK 13 останавливается при загрузке
`libgdx.dylib` из существующих зависимостей. Та же ошибка воспроизводится
на исходном `hometask-2` до создания сцены; визуальная проверка не выполнена.
